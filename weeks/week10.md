# W10：用户反馈、迭代与交付

本周继续使用 W9 的产品，从 `course/main` 创建 `week10/delivery` 分支。你将邀请同学试用，根据观察和反馈完成一次需求变更，再整理代码、文档和演示材料，使他人能够安装并使用产品。

## 概念与引导示例

先回看 W4 的任务交接、W7 的代码审查和 W9 的运行记录，选出本周迭代需要使用的方法。试用任务应当描述用户要完成什么，验收场景则说明修改后怎样判断任务已经完成。

例如，用户说“找不到报告”，说明他在某一步遇到了困难；“把按钮放大”只是一种可能的解决方案。先了解他当时在做什么，再分析按钮的位置、名称或操作顺序，最后确定修改需求。使用[反馈模板](../materials/templates/feedback.md)分别记录观察、原因解释和需求。

## 1. 开展交叉试用

与一位同学互相试用产品，两人分别维护自己的代码和 PR。在本机环境或按文档安装的环境中，给对方固定图表和以下任务目标，让对方独立操作：

1. 找出并解释图中问题；
2. 定位图元并修改；
3. 确认问题是否解决；
4. 导出并说明报告内容。

记录各项任务是否完成，以及操作路径、停顿、提问和理解偏差。观察结束后询问原因；采集截图或录屏前征得对方同意。案例不包含个人数据。

## 2. 根据反馈完成一项跨模块修改

整理反馈，区分功能缺陷、操作理解上的困难和新增需求。选择一项对用户有明确帮助、涉及至少两个模块或状态的修改。例如，过期报告的处理可能同时涉及状态判断、重查按钮和导出提示；定位失败的恢复可能涉及画布桥接、结果列表和错误提示。

实现前，写明需求变化、成功条件、影响范围和回归场景，并比较合理的解决方案。然后向 Agent 提供当前设计、相关代码和试用记录，完成修改后阅读 diff，开展代码审查并运行回归测试。

回访原试用者，重复相关任务，记录变化。分别写出用户的实际反馈与自己的解释。

## 3. 完成交付包

产品仓库包含：

- 产品目标和用户工作流；
- 安装、启动、模型配置与连通性方法；
- CLI 用法、规则、配置及报告格式；
- 自动化验证命令和固定人工案例；
- 运行手册、故障恢复与观测；
- 本学期 PR 与报告索引。

交付说明应使读者能够独立运行固定图表检查。AI 修改部分另写明所用 `provider`、`model`、凭据配置位置和连通性检查方法。

## 4. 在独立目录按文档安装并验证

先提交并推送本周反馈迭代及交付文档，将该版本的完整 SHA 写入记录，作为本次交付候选。再在独立目录克隆自己的 fork，切换这个 SHA，运行 npm ci。按文档运行类型检查、相关测试、CLI 构建与检查、产品构建和生产启动。浏览器完成多页定位、修改重查、报告导出和版本恢复。

记录实际命令与输出，核对交付文档是否遗漏步骤。修正文档或实现后重跑受影响流程。

## 5. 演示工程过程

按一条实际用户任务展示：

用户问题 → 需求与方案 → Agent 开发 → 测试与审查 → 产品使用 → 故障恢复 → 反馈迭代。

演示至少包含多页图表、问题定位、手工或 AI 修改、重查、报告比较和导出。再选择一次影响实现的 Agent 建议或代码修改，说明你怎样核对它，以及作出了什么决定。

## 6. 写个人复盘

引用具体 PR、提示、交接、测试和运行记录，解释：

- 哪些上下文改变了 Agent 的计划或代码；
- 哪些决定由自己作出，为什么；
- 哪种验证发现了问题，怎样确认修复；
- 任务拆分和交接哪里有效；
- 下一次会保留和改变什么。

围绕关键决策、行为变化和验证结果，选择代表性证据形成连贯解释。

## 提交内容与完成标准

提交本周跨模块修改、用户试用记录、交付文档和演示材料，并在 `course-notes/W10.md` 中完成个人复盘。通过最终 PR 合并这些内容，使八次作业和最后两周的代码、报告与 PR 能够相互查阅。

- 产品可从干净目录复现；
- 反馈落实为有验收场景的已验证变更；
- 演示覆盖完整用户工作流；
- 复盘对应真实工程材料；
- 八次作业与最后两周的代码、PR 和报告可以相互追溯。
