## 概念与材料

阅读 [Incident Response & DevOps](../materials/slides/week09-1117-incident-response-devops.pptx)与 [Resolve](../materials/slides/week09-1121-resolve-guest-lecture-slides.pdf)。关注怎样从现象提出假设、寻找证据和验证恢复。

计时与诊断概念见[导读](../docs/primer.md)。先做一个阅读练习：为同一任务列出 `started`、`failed`、`retried`、`completed` 四条事件，并使用相同的 `taskId` 标识它们。比较仅查看最终错误与查看整个事件序列时，你分别能判断什么。

## 1. 构建产品并记录初始运行结果

从产品根目录执行：

```powershell
npm run build
npm run start
```

在 [localhost:6001](http://localhost:6001) 打开应用，用固定图表完成检查、定位和导出。记录 Node 版本、构建对应的提交、浏览器、机器和配置，作为本周实验的初始条件。编写代码时可以使用开发服务，本周的性能测量和恢复后验证使用生产构建。

## 2. 记录检查任务的运行过程

为每次检查保存结构化事件，记录任务开始、解析、规则执行、报告生成，以及完成、失败、取消或结果过期。事件中包含 `taskId`、`fingerprint`、`scope`、配置摘要、页面和图元数量、各阶段耗时及错误类别。

这些信息用于回答两个问题：一次任务停在哪个阶段，以及报告是否对应当前图表。相同任务使用同一个 `taskId`，输入摘要则用于核对内容是否变化。

默认不记录标签正文、完整提示、API key 或 `.env` 内容。提供一份正常任务和一份失败任务的事件记录，说明怎样从记录中区分以下故障：

- 浏览器检查核心与状态错误；
- 应用服务不可用；
- 模型请求失败；
- 画布资源或桥接未就绪。

根据故障来源，向用户提示重试、重新检查图表或检查配置。选取必要的事件片段交给 Agent 诊断，再核对它提出的假设是否与记录一致。

## 3. 完成三类故障演练

按[故障注入材料](../materials/labs/fault-injection.md)构造：

| 故障 | 操作与观察 | 恢复后确认 |
|---|---|---|
| 画布资源不可用/未就绪 | 在浏览器测试中阻断 iframe 资源请求，观察画布未就绪时的提示 | 撤销拦截并重新加载，可检查和定位 |
| 检查中输入变化/任务替换 | 在 HW8 的测试执行器中控制 A/B 顺序，并编辑文档 | 重新检查最新快照，确认旧任务结果没有覆盖新任务 |
| AI 修改失败/中断 | 浏览器测试从外部返回 503 或中断流，观察版本与提示 | 恢复响应后完成修改并重查 |

每项演练记录用户看到的现象、初始假设、排查操作、判断依据、恢复步骤和恢复后结果，同时说明执行环境。网络故障可以通过浏览器测试拦截本地生产服务的请求来模拟；A、B 任务的指定完成顺序使用测试中的可控执行器复现。应用内部用于故障注入的开发开关在生产构建中关闭。

完成故障测试后，使用真实执行器，在未注入故障的生产构建中再次执行编辑、检查、定位、导出和版本恢复。核对 `taskId` 与输入摘要，确认显示的是恢复后的新结果。报告中分别记录可控故障测试与生产构建中的实际操作。

## 4. 完成性能实验

在课程根目录生成输入：

```powershell
python tools/make_cases.py --performance .runtime/performance-inputs --with-issues
```

命令生成三份分别含 10、500、4900 个节点的图表，计入连接和结构根节点后，分别为 21、1001、9801 个图元。每五个步骤有一个空白名称，使规则执行、报告生成和结果列表显示都包含待处理问题。将输入复制到产品的本地运行目录。

每种规模先预热 3 次，再测量 10 次。记录解析、规则执行、报告生成和总耗时，同时观察界面能否及时响应操作。CLI 测量包括文件读取和检查核心；浏览器实验还需观察问题列表渲染。两类数据分别报告，说明测量包含哪些阶段。生成目录中已有同名文件时，使用新目录，保留前一轮输入。

保存原始样本，报告中位数、最小/最大值与测量条件。测量前固定配置、范围与是否使用开发工具。

根据测量结果，选择重复解析、规则查找、排序、列表渲染或任务调度中的一项实际开销进行优化。先说明为什么认为它是主要开销、计划怎样修改，以及预期影响，再使用相同输入复测。比较报告时排除 `generatedAt`，核对问题与统计保持一致，并分析数据是否支持原假设。

## 5. 编写运行手册并按文档复现

手册需要说明环境要求、安装、构建、启动和配置方法，以及在哪里查看运行记录。针对演练中的常见症状，给出排查顺序、恢复操作和恢复后的验证命令。

在另一个干净目录从自己的 fork 和候选提交安装，按手册完成流程。保留本地未提交成果，复现目录使用独立路径。

## 提交内容与完成标准

提交运行记录代码、故障测试、性能优化和回归测试。在 `course-notes/W9.md` 中整理原始数据索引、三项故障演练和运行手册，通过本周 PR 合并。

- 每项故障能够稳定触发和恢复。
- 能够根据运行记录区分浏览器代码、应用服务、模型请求和画布资源故障。
- 性能结论有优化前后的测量数据支持，问题列表和统计保持一致。
- 干净目录可按手册复现，生产默认不注入故障。
