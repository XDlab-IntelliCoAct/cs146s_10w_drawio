# HW5：将检查能力接入终端和 CI

**安排：W5。** 继续使用 HW4 的检查核心、配置与报告，在 `hw05/cli-ci` 分支开发。学习顺序见[W5](../weeks/week05.md)。

## 本次作业要解决的问题

开发者希望一次检查多个图表文件，在 PR 中自动运行检查，并下载报告查看结果。本周复用 HW4 的检查核心，实现命令行工具、报告比较和 CI。终端与 CI 应使用相同的规则和退出码，使本地结果能够解释自动检查的成败。

## 实现步骤

### 1. 定义命令界面

按照[CLI 约定](../docs/contracts.md)实现 `course:check` 与 `course:compare`。使用项目已有的 `esbuild` 打包供 Node 执行的代码，并添加 npm 脚本，使使用者安装依赖后可以按文档运行。

先编写 `--help`，列出正常和失败时的调用示例，再实现参数解析。输入支持单个文件或目录；配置可以使用内置 ID，也可以指定 JSON 文件路径。帮助文字应让使用者知道命令做什么、结果保存在哪里，以及失败时怎样判断原因。

添加 `course:build` 脚本，将 CLI 打包到指定构建目录。可以让两个执行命令自动先构建，也可以要求使用者和 CI 先运行 `course:build`；无论选择哪一种，都要在说明中写清，并从独立的新目录按步骤验证。打包时核对 `@/` 路径别名能够解析，浏览器专有对象没有被引入 Node 执行路径。

### 2. 实现批处理和文件行为

目录输入只处理当前层的 `.drawio` 文件，按稳定顺序执行，不跟随符号链接。某个文件无效时，继续检查其他文件，并在批次报告中保留每项结果及 `completed`、`failed` 数量。这样，一份坏文件不会使整批已完成的结果丢失。

实现 `--output`、`--force`、`--fail-on` 和 `--dry-run`。写入前，检查输出是否与输入同路径、目标是否已存在，以及父目录和权限是否允许写入。写入失败时保留原有报告。`dry-run` 只检查参数、配置和文件处理计划，不解析图表内容、不执行规则，也不创建目录或报告文件。

命令示例从产品根目录运行：

```powershell
npm run course:check -- --input course-fixtures/normal.drawio --output .runtime/normal.json
npm run course:check -- --input course-fixtures/batch --fail-on warning --output .runtime/batch.json
npm run course:check -- --input course-fixtures/batch --dry-run
```

批次案例包含无效 XML，因此最终退出码应为 `2`，报告中仍保留其他三项结果。`normal` 的退出码应为 `0`；`labels` 只有警告，在默认错误阈值下返回 `0`，使用 `--fail-on warning` 时返回 `1`。测试中启动子进程并读取实际退出码，同时核对报告内容。

### 3. 实现报告比较

分别保存修改前后的报告，再用比较命令的 `before`、`after` 参数读入，列出新增、已解决和持续存在的问题。比较依据问题标识进行，因此只改变 `message` 或 `generatedAt` 不应产生新问题。配置变化单独提示；检查范围或报告版本不兼容时，应说明原因并拒绝比较。

分别构造四种情况：补充名称后原问题消失，新增错误引用后出现新问题，只修改生成时间时问题不变，切换配置后相应规则的结果发生变化。

再输入一份 `invalid` 报告，确认比较命令说明该报告不可比较，并返回退出码 `2`。未完成的检查无法给出问题结论，因此其中的空列表不能被视为问题已经解决。

### 4. 接入个人 fork 的 CI

在个人产品 fork 中新增课程检查工作流，监听目标分支为 `course/main` 的 PR。工作流使用 Node 24 和 `npm ci` 安装依赖，依次运行类型检查、相关测试、CLI 构建及正常样例检查，最后将 JSON 报告上传为可下载的构建产物（artifact）。

工作流使用 `pull_request` 事件并限定目标分支为 `course/main`。如果用 `paths` 只监听相关功能和案例文件，也要包含工作流自身。报告上传步骤设置为前序检查失败后仍执行，使用户能下载已生成的报告；如果报告未生成，应在日志中说明原因。

先让正常 PR 成功。另建一项演示 PR：把已知错误图表作为检查输入，使检查以预期退出码失败；保存运行链接后关闭该演示 PR，不合并到 course/main。

在自己的 fork 实际运行工作流并检查日志。若账号的 Actions 不可用，保存具体提示与本地等价命令结果，向教师报告配置问题。

首次使用个人 fork 的 Actions 时，先在 Actions 页面查看是否需要启用复制的工作流，并按页面提示完成。新 PR 没有运行记录时，依次检查工作流是否启用、base 分支是否为 course/main、事件与路径条件是否匹配。

### 5. 使用 Agent 诊断失败

至少诊断一项工作流失败。没有自然失败时，使用[配置错误案例](../materials/labs/ci-failure.md)。提供需求、运行输出与最小上下文，让 Agent 定位、修改、复跑。

诊断报告需要说明：失败是配置无效、图表问题达到阈值，还是程序无法完成检查。根据实际原因修复并复跑，核对退出码仍符合共同约定。

## 提交内容

提交 CLI、npm 脚本、报告比较、子进程测试和 Actions 工作流。在使用说明中给出可运行命令，在 `course-notes/HW5.md` 中提供成功与预期失败的 CI 链接、报告位置，以及 Agent 诊断失败的过程。通过本周 PR 合并正常工作流。

## 完成标准

- CLI 调用 HW4 检查核心，相同输入在终端与界面中得到一致的问题和统计。
- 单个文件失败后仍继续处理批次；失败阈值、覆盖保护、dry-run 和退出码符合约定。
- 比较结果不受时间和排序影响。
- 正常 CI 通过，演示 CI 因预期原因失败，报告可以下载。
- 对工作流失败的解释对应日志与复跑结果。
