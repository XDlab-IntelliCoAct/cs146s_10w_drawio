# HW3：在真实项目中交付第一个检查功能

**安排：W3。** 从[固定教学版本](../docs/baseline.md)开始，在个人产品 fork 中使用自己的 Coding Agent 开发。准备和阅读顺序见[W3 学习页](../weeks/week03.md)。

## 本次作业要解决的问题

用户导入流程图后，希望知道哪些流程步骤缺少名称。点击检查后，界面需要列出问题所在的页面、图元和原因；补充名称并重新检查后，该问题应当消失。你将围绕这项功能阅读项目、明确需求、选择接入方式，并验证从用户操作到结果显示的完整过程。

## 开始前：建立运行基线

本周切换到 TypeScript 产品开发。HW1、HW2 中分析规格、定义工具接口和验证行为的方法可以继续使用；产品读取图表、转换数据和检查名称的代码需要在本周实现。

按[环境准备](../docs/setup.md)创建个人 fork 和 `course/main` 分支，安装依赖并启动应用。修改前先运行类型检查、相关测试和构建，记录命令与版本；如果失败，保存第一条错误和当时的输出。

打开 normal.drawio，修改、导出并重新打开。说明开发服务、生产构建、模型服务、draw.io 资源分别提供什么。

在产品根目录创建 hw03/first-check 分支。将课程 materials/fixtures 复制为产品的 course-fixtures；按自己实际课程路径设置变量：

```powershell
$course = '你的课程仓库绝对路径'
Copy-Item -LiteralPath "$course/materials/fixtures" -Destination course-fixtures -Recurse
```

## 实现步骤

### 1. 从问题出发读源码

按[源码导航](../docs/source-map.md)中标记为 HW3 的条目阅读。追踪导入操作怎样更新 `chartXML` 和 `currentPageId`，用户编辑、导出和恢复版本时数据又怎样变化。画一张数据流图，标明实际文件与函数或状态名称。

阅读后，为计划新增的每个模块说明职责。本周默认检查整个文件，因此需要回答：怎样取得全部页面？在什么时候读取 XML 才能包含用户最新的编辑？检查结果保存在哪里？规则放在哪个模块中，才能供其他程序调用并单独测试？

### 2. 写出用户需求与行为样例

按[角色与名称约定](../docs/contracts.md)，明确步骤、标题、注释、装饰的区别。列出用户操作、输入和预期结果：

| 输入 | 操作 | 预期观察 |
|---|---|---|
| normal | 检查 | 没有缺名问题 |
| labels | 检查 | page-a/n2 缺名 |
| html-label | 检查 | 只有格式标记和空格仍是缺名 |
| grouped | 检查 | 空标题和装饰不作为缺名步骤 |
| empty | 检查 | 成功完成，说明图中没有步骤 |
| multi-page | 检查全部页 | 问题定位到 page-b/n2 |
| invalid | 导入/直接适配 | 应用可能拒绝导入；适配层直接输入时明确报错 |

另外设计一组正常与异常样例。无效文件可能在导入时被拒绝或修复；验证数据适配层的异常处理时，直接将原始内容传入适配函数，使测试能够稳定触发错误。

### 3. 为 Agent 准备上下文并选方案

填写[上下文模板](../materials/templates/agent-context.md)，包含运行命令、需求、源码与样例。

让 Agent 比较两种合理的接入方案。例如，检查结果可以保存在开发组件的局部状态中，也可以由独立状态模块管理。结合哪些代码需要读写结果、后续怎样共享，以及本次改动范围作出选择，并在报告中说明理由。

### 4. 实现检查函数并接入界面

- 读取图表快照，将页面、节点和图元角色转换为检查所需的数据。
- 实现 `missing-label`，在每项问题中保留 `pageId` 和 `cellId`。
- 在开发环境增加检查按钮与最小结果列表。
- 在结果区分别显示空图、检查完成且无问题、检查完成且有问题和执行失败。
- 将名称作为安全文本显示，检查过程不修改原图表。
- 将检查逻辑组织为可独立调用的函数，供后续规则和 Node 命令复用。

先完成可以独立调用的检查函数，再连接界面操作。检查函数使用 Node 和浏览器都能处理的数据结构，界面组件负责发起检查和显示结果。每完成一个部分，就运行相关测试，并阅读 diff，核对 Agent 的修改是否符合预期。

先在测试中输入 `normal` 和 `labels`，确认检查函数返回预期结果，再连接按钮和列表。最后使用 `multi-page` 验证问题属于 `page-b/n2`。本周列表显示页面和图元 ID；点击问题后切页与高亮的交互在 HW8 实现。

### 5. 核对并提交

完成上表与自己的样例；在真实浏览器中做“导入 → 检查 → 补名 → 重查 → 导出”。运行类型、相关测试和构建。按[提交方式](../docs/collaboration.md)创建个人 PR。

## 提交内容

提交功能代码、固定案例和测试。在 `course-notes/HW3.md` 中说明源码的数据流、用户需求、两种接入方案及选择理由，并记录给 Agent 的上下文、实际代码变更、测试结果和浏览器操作结果。

## 完成标准

- 能解释用户操作到结果的真实路径。
- 名称检查按可读文本与图元角色判断，页面定位正确。
- 原有导入、编辑、保存和导出可继续使用。
- Agent 建议与自己的设计决定有区分。
- PR 的结论由实际命令和操作支撑。

如果名称判断错误，先核对原始 `value`、提取后的可读文本和图元角色。如果结果没有反映最新编辑，则检查读取数据的时机和保存的输入快照。概念支持见[W3 导读](../docs/primer.md)。
