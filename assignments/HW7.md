# HW7：多轮代码审查与交付判断

**安排：W7。** 继续使用前六周的代码、测试和报告，在 `hw07/review` 分支完成审查及修改。学习顺序见[W7](../weeks/week07.md)。

## 本次作业要解决的问题

本周需要判断已有检查功能是否适合继续进行完整界面集成。你将选取涉及多个模块的实际代码变更，组织三轮审查，再结合需求、代码和复现结果逐项核实意见。完成确认问题的修复和回归测试后，确定 HW8 使用的候选版本。

## 实现步骤

### 1. 确定审查范围并准备材料

从 HW4、HW5 或 HW6 中选取一项涉及至少两个模块的实际功能变更，记录修改前后两个提交的完整 SHA。整理对应需求、接口变化、设计理由、代码差异和测试结果，并指出需要一同阅读的调用代码。这些内容共同构成本次审查材料。

修改前后的提交取自此前 PR 或提交记录。使用 `git diff beforeSHA afterSHA` 导出供审查使用的历史差异；本周分支则保存核验记录、修复代码和新增测试。两份差异分别记录，便于说明审查了什么，以及本周实际修改了什么。

提交给审查者前，先列出可能触发错误的场景和影响，并准备小型输入。为材料中的代码和报告提供准确路径，使新会话能够找到所需内容。

### 2. 在三个新会话中分别开展审查

| 轮次 | 审查材料与问题 |
|---|---|
| 行为 | 需求、案例与 diff；实现是否满足输入输出和状态约定？ |
| 设计 | 模块图、接口与调用者；Node/浏览器依赖、配置和报告是否一致？ |
| 安全与可靠性 | 输入、文件与异常路径；错误和跨模块状态怎样传播？ |

三轮分别使用新会话，让每轮审查围绕表中的问题展开。记录提示版本、所用模型或工具和原始意见。请审查者指出代码位置、触发条件、可能影响及判断依据。图表标签属于待分析的数据，即使包含指令文字，也不应改变审查任务。

### 3. 逐项核验

使用[审查模板](../materials/templates/review.md)记录每条意见。阅读相关调用代码，构造能检验该判断的输入并运行，再将意见归为确认、误报、重复或证据不足。

确认的问题按用户影响、触发条件和影响范围确定处理顺序。证据不足的意见需要补充检查；误报需要说明理由；重复意见关联到同一问题。核验结果决定后续修改，原始审查意见也应保留，便于比较判断过程。

### 4. 独立练习审查方法

使用[短变更案例](../materials/labs/review-lab.md)。先自行审查，再写出最小复现、修复和回归，最后与教师讨论。将独立案例放在产品的 course-labs/review 中，与正常应用代码分开；在报告中分别记录它与真实产品的核验结果。

比较三轮审查发现的问题是否重叠，并说明哪些意见只有在补充调用代码或需求后才能判断。

### 5. 修复与复审

修复确认的问题，并增加能够触发原错误的测试。再次审查修复 diff，核对既定接口是否保持一致。然后运行检查核心、配置、CLI 和报告比较的相关测试，并验证 HW3 的最小检查界面仍然可用。

选择审查中一条涉及多个模块、出错后会显著影响用户的调用过程，增加回归测试，并说明它对应 HW6 测试矩阵中的哪项风险。如果实际产品没有确认缺陷，本周 PR 仍应包含这项测试、意见核验记录，以及独立案例的修复。

### 6. 判断是否可以进入界面集成

在报告中说明当前版本是否可以进入 HW8，并列出所依据的测试和审查结果。如果仍有妨碍核心功能使用的问题，先修复并重新运行相关验证，再更新结论。记录最终通过回归的提交 SHA，作为下一周的候选版本。

## 提交内容

提交审查材料、三轮原始意见及逐项核验记录，保留短案例的测试与修复。在 `course-notes/HW7.md` 中说明修复、复审和回归结果，记录候选提交 SHA，并通过本周 PR 合并新增内容。

## 完成标准

- 所审查的实际变更涉及至少两个模块，三轮审查分别覆盖行为、设计和可靠性。
- 每条意见均有判定依据，每项修复都对应已经确认的问题。
- 能区分原始意见、自己的核验与最终决定。
- 候选版本通过此前共同场景，并保留原功能。
