# 概念与引导示例

本页结合各周任务解释新概念。开始作业前，先阅读本周对应的小节，再将其中的方法用于具体实现。有些示例供你阅读和推演；附有运行命令的示例可以按说明执行。

## 经常出现的词

| 术语 | 在本课程中的含义 |
|---|---|
| fork | 复制到自己账号下的仓库；课程和产品分别有自己的副本 |
| PR（拉取请求） | 用来展示、讨论并合并一次分支变更 |
| diff | 两个版本的代码差异；用于核对 Agent 实际改了什么 |
| CLI（命令行工具） | 在终端接收参数、执行检查并返回结果的程序 |
| CI（持续集成） | 在提交或 PR 后自动运行测试、检查和报告生成 |
| schema | 描述字段、类型和必需项的数据格式约定 |
| 快照 / snapshot | 某一次读取时的完整数据副本 |
| 内容摘要 / fingerprint | 根据内容计算的固定长度标识，用于判断内容是否变化 |
| 适配器 / adapter | 将文件或外部状态转换成核心能够处理的数据 |
| 回归测试 | 修改之后重跑相关旧场景，检查原有行为是否保持 |

## W1：规格、schema 与评估

图表规格说明模型输出应当包含哪些步骤、连接和待确认信息。JSON Schema 则规定这些数据使用哪些字段、字段是什么类型，以及哪些字段必须存在。

例如，`{"nodes":[],"edges":[],"questions":[]}` 可以符合字段类型要求。如果用户描述了三个明确的步骤，这份输出却没有保留任何步骤。因此，程序需要检查数据格式，你还需要对照用户描述判断内容是否准确。

先以“打印店收件，再通知取件”为例，手工列出两个节点及其连接，然后对照模型输出，检查它是否保留了这段描述。实验中，开发集用于发现问题和调整提示；评估集用于检查定稿后的方案。每次修改后保留版本号，使结果能够对应到实际使用的提示和配置。

## W2：工具、循环和版本

模型可以提出“修改节点 n2 的名称”，实际写入文件的是工具程序。程序应先检查 n2 是否存在，并确认文件仍是先前读取的版本。否则，在模型思考期间，用户或另一个程序可能已经修改文件，本次写入就会覆盖这些变化。

课程使用文件字节的 SHA-256 摘要表示版本。读取时保存摘要，写入前重新计算并比较；两者不同，就拒绝本次修改并要求重新读取。

运行 W2 学习页中的 `adapter_demo`，可以看到节点改名后版本摘要发生变化，再用旧版本请求写入时会得到 `version_conflict`。Agent 程序记录并回传这次工具错误，然后按错误类型决定能否重试。

## W3：从 Python 到 TypeScript

| Python 中熟悉的写法 | TypeScript 中阅读的对象 |
|---|---|
| dict | 对象；类型说明允许的字段 |
| list[dict] | interface[] 或 Array<Type> |
| def | function 或箭头函数 |
| await | 等待异步结果；调用者也需处理异常 |
| None | null/undefined；含义需看接口 |
| 模块导入 | import；@/ 是项目路径别名 |

React 组件负责显示界面并响应操作。组件通过 props 接收外部数据，通过 state 保存会影响界面显示的数据；state 更新后，React 会重新计算界面。ref 也能保留值，但修改它不会触发重新渲染。

阅读项目时，先找到图表数据保存在哪个组件或状态模块，以及谁负责更新它。检查结果需要与这份数据保持一致，因此应在理解现有状态管理后，再决定结果保存在哪里。

### 一个不同功能的 PR 示例

任务：在本地练习组件显示用户输入的字符数。

```tsx
function CountHint({ text }: { text: string }) {
    return <output aria-label="字符数">{Array.from(text).length}</output>
}
```

这项练习采用 Unicode code point 计数，空输入显示 0。测试时分别输入空字符串、中文和 emoji，再到浏览器中输入文本，观察计数是否随之更新。这里需要先确定“字符数”的定义，再让 Agent 实现，并据此编写测试。

PR 描述可以写为：“输入变化时，组件会更新按 Unicode code point 计算的字符数。组件测试覆盖空字符串、中文和 emoji；另在浏览器中确认键盘输入后计数能够更新。”

## W4：适配器、纯函数与交接

图表文件使用 XML 保存，而规则更适合直接处理页面、节点和连接组成的数据。适配器负责完成这种转换。转换后的检查核心只根据传入的数据计算结果，不修改输入，也不从 React 或其他全局状态中取数据。这样的函数可以在浏览器、CLI 和测试中调用。

可以先用 `countItems(items)` 练习接口说明：输入空数组时返回 0，输入 `null` 时返回“未知”。将说明和样例交给一个新会话，请它编写调用代码。观察它是否正确区分“数量为零”和“无法确定数量”，再将同样的方法用于本周的模块交接。

## W5：退出码与批处理

命令行工具既要向人说明结果，也要让自动化脚本判断是否继续。终端摘要用于说明检查了哪些文件、发现了什么；退出码是程序结束时返回的整数，脚本据此判断本次执行是否成功。

“检查完成，发现缺名警告”和“文件无法读取，检查未完成”具有不同含义。先按作业约定列出退出码，再编写子进程测试，同时检查标准输出、标准错误和退出码。

例如，程序依次统计两个文本文件的行数。如果第二个文件不存在，它仍应保留第一个文件的结果，并在最后列出失败的文件。图表批量检查采用相同的处理思路。

## W6：测试层次与变形关系

不同层次的测试回答不同问题。单元测试用于检查一条规则的判断，模块集成测试用于检查解析、规则和报告能否配合工作，子进程测试用于验证实际命令的退出码与文件操作，浏览器测试则验证用户能否通过界面完成任务。

除了为固定输入列出标准答案，还可以利用输入变化前后的关系设计测试。例如，将所有图元坐标都加 10，名称和连接关系没有变化，结构检查结果也应保持一致；删除一条连接则可能使某个步骤成为孤立步骤。先说明这种关系成立的条件，再写程序断言，这类测试称为变形测试。

## W7：核验审查意见

收到审查意见后，需要回到代码和需求中核实。例如，“空数组会导致崩溃”是否成立，取决于程序怎样访问数组：读取 `items.length` 可以得到 0，访问 `items[0].name` 则会因第一项不存在而报错。检查调用者是否可能传入空数组，再构造相应输入，才能判断这条意见是否适用于当前程序。

记录意见时，写明代码位置、触发条件、用户受到的影响，以及核验所用的输入或测试。确认问题后再修改，并用同一个输入检查修复结果。

## W8：快照与异步结果

检查需要一定时间，期间图表可能发生变化。因此，每次检查都保存开始时的完整文档副本，称为输入快照，并用 `taskId` 标识这一次任务。报告描述的是该快照中的问题。

如果新任务 B 已经开始，旧任务 A 随后才返回，A 的结果不能覆盖 B。如果检查期间用户修改了图表，返回的报告仍可保留，但界面应标明“结果已过期”，提示用户重新检查。这样，用户能区分历史报告与当前图表的状态。

W8 学习页提供了一个搜索结果顺序示例。先预测旧请求晚返回时界面会显示什么，再运行脚本，比较是否检查任务标识所造成的差别。

## W9：观测与恢复

运行记录中的 `taskId` 用于找出属于同一次检查的事件。将开始、解析、规则执行和最终状态按顺序查看，可以判断错误发生在哪个阶段。

性能实验应使用一致的计时方法。先预热，使首次加载等开销与后续测量分开，再保存多次测量的原始数据，报告中位数和范围。

故障恢复后，还需要重新执行用户任务。例如，画布重新加载后，再次检查并定位图元，确认这些操作已经恢复；仅看到错误提示消失，还不足以说明任务可以完成。

## W10：从反馈到变更

用户在操作时说“找不到按钮”，描述的是使用中遇到的困难。“把按钮放大”则是一种可能的解决方案。先了解用户当时的目标和操作过程，再分析按钮的位置、名称或视觉层级，才能选择适当的修改。

使用[反馈模板](../materials/templates/feedback.md)分别记录实际观察、原因解释、修改需求和验证结果。修改后请试用者重复原任务，检查先前的困难是否得到解决。
